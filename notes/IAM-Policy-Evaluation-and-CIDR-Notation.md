# IAM Policy 评估逻辑 & CIDR 网段表示法笔记

## 一、题目场景：RDS MySQL 读写分离，应用性能下降

公司总部的应用访问存放在 Amazon RDS MySQL DB instance 里的产品数据，运维团队发现性能下降，想把读流量和写流量分开。

### 正确答案：创建 Read Replica，配置和源数据库**相同**的计算和存储资源

- Read Replica 需要持续追赶(replicate)主库的写入。如果副本资源明显低于主库（比如砍一半），副本容易产生**复制延迟(replication lag)**——主库写入速度超过副本处理能力，副本数据越来越滞后，读到的是过时数据，达不到"优化性能"的目的。
- AWS 最佳实践：Read Replica 配置与源库**相同**的计算/存储资源，才能保证有足够能力跟上主库写入速度，稳定承接读流量。

### 为什么不是"配置一半资源"
省成本没有依据，反而会造成复制延迟和读性能不足，治标不治本，是本题的干扰项，专门测试是否会因为"想当然省成本"而选错。

### 为什么不是 Multi-AZ 方案
Multi-AZ 的 **standby(备用)实例不可读**，不能处理读请求——这是反复出现的高频考点。Multi-AZ 解决的是**高可用/容灾**，不是"读写分离/读扩展"问题，跟本题要解决的"性能瓶颈"目标不对应。

### 这个"读写分离"功能和 Aurora 是什么关系
**Read Replica 不是 Aurora 独有的功能**，普通 RDS（MySQL/PostgreSQL/MariaDB/SQL Server 等）本身就自带这个功能，出现得比 Aurora（2014年发布）还早。本题场景明确是"普通 RDS MySQL"，不是 Aurora。

两种 Read Replica 的底层实现差异：

| | 普通 RDS Read Replica | Aurora Replica |
|---|---|---|
| 复制方式 | 基于 **binlog 异步复制**，副本要重放主库日志 | 共享同一份底层存储，不用真正复制数据 |
| 复制延迟 | 有明显延迟（几百毫秒到几秒），取决于负载和副本性能 | 延迟极低（约10-20毫秒），接近实时 |
| 对副本资源的敏感度 | **高**——资源不足容易导致延迟增大（本题考点） | 相对没那么敏感 |
| 最多副本数 | 视引擎而定，通常约5个 | 最多15个 |
| 能否自动故障转移 | 部分场景可手动提升(promote)，非无缝自动 | 可配置自动故障转移 |

结论：Aurora Replica 是"更先进、更彻底"的读写分离方案，普通 RDS Read Replica 是"较早期、较传统"的方案（对副本资源配置更敏感）。这道题限定"已经在用普通 RDS MySQL、要尽快优化"，不涉及换引擎，所以直接在现有 RDS 上配置资源对等的 Read Replica 就是最快、最合理的答案。

## 二、题目场景：一段 IAM Policy 的实际效果判断

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "ec2:TerminateInstances",
      "Resource": "*",
      "Condition": {
        "IpAddress": { "aws:SourceIp": "10.100.100.0/24" }
      }
    },
    {
      "Effect": "Deny",
      "Action": "ec2:*",
      "Resource": "*",
      "Condition": {
        "StringNotEquals": { "ec2:Region": "us-east-1" }
      }
    }
  ]
}
```

### 拆解两条语句

- **语句一(Allow)**：允许 `ec2:TerminateInstances`（终止实例），**没有 Region 限制**，唯一条件是来源 IP 落在 `10.100.100.0/24` 网段内（即 `10.100.100.0` ~ `10.100.100.255` 全部256个地址）。
- **语句二(Deny)**：拒绝**所有** EC2 操作(`ec2:*`)，条件是 Region **不是** `us-east-1`。因为 **IAM 里 Deny 永远优先于 Allow**，这条规则把语句一允许的操作也一并限制住了——只要不在 `us-east-1`，无论 IP 是否在允许范围内，一律禁止。

### 合并后的实际效果

用户能终止 EC2 实例，必须**同时满足**：① 来源 IP 在 `10.100.100.0/24` 内；② Region 是 `us-east-1`。不在 `us-east-1` 时，不管 IP 是什么，一律拒绝。

### 选项分析（易错点）

- 选项写"IP `10.100.100.1` 在 us-east-1"和"IP `10.100.100.254` 在 us-east-1"这两种描述，**从纯 CIDR 逻辑看是完全等价的**——因为 `/24` 网段本来就覆盖 `.0` 到 `.255` 全部256个地址，`.1` 和 `.254` 都毫无疑问落在范围内。这是这道经典真题本身设计不够严谨的地方（两个选项理论上都成立），但官方标准答案取的是 IP `10.100.100.1` 那个选项。
- "除了 us-east-1 都能终止实例"——方向反了，语句二是"不在 us-east-1 就拒绝"，不是"us-east-1 里拒绝、别处允许"。
- "IP `.254` 在 us-east-1 不能终止"——错，`.254` 明明在允许范围内且 Region 正确，应该是被允许的。

### 这道题真正考察的核心知识点

> Allow 语句里用 IP 条件做限制 + Deny 语句里用 `Region != us-east-1` 做兜底限制 → 合起来的效果是"只有这个 IP 段、且只在 us-east-1，才能终止实例"。

**做题通用技巧**：读 IAM Policy 永远要**先看 Effect 是 Allow 还是 Deny**，再看 Condition 的具体限制条件；**Deny 优先于 Allow**；多条 Statement 要合并起来看最终效果，不能只看单条语句就下结论。

## 三、CIDR 网段表示法：`/24` 到底是什么意思

### IP 地址的二进制结构

一个 IPv4 地址（如 `10.100.100.5`）由 4 段十进制数字组成，每段对应 **8 位二进制**，四段共 32 位：

```
10      . 100      . 100      . 5
00001010.01100100.01100100.00000101
  8位   .   8位   .   8位   .  8位
```

### `/24` 的含义

`/24` 叫 **CIDR 前缀长度(prefix length)**，意思是：**从左边数起，前 24 位固定不变（网络部分），剩下 32-24=8 位可以任意变化（主机部分）**。

`10.100.100.0/24` 拆开看：前 24 位 = 前 3 段(`10.100.100`)固定死；后 8 位 = 最后一段，可以是 0-255 任意数字。所以它代表的不是"一个 IP"，而是**一整个网段**——只要前三段是 `10.100.100`，最后一段不管是几都算在内，一共 **256 个地址**（2^8=256）。

### CIDR 数字的规律：数字越大，范围越小

| CIDR | 固定位数 | 可变位数 | 地址数量 | 直观理解 |
|---|---|---|---|---|
| `/32` | 32位全固定 | 0位 | 1 个 | 精确指定单个 IP，不是网段 |
| `/24` | 前3段固定 | 最后1段可变 | 256 个 | 常见的"一个小型局域网" |
| `/16` | 前2段固定 | 后2段可变 | 65536 个 | 更大的网段 |
| `/0` | 0位固定 | 全部可变 | 所有IP | "任意IP"，常见于安全组 `0.0.0.0/0`（对全世界开放） |

**记忆技巧**：`/32` = "只指这一个人"，`/24` = "这一整栋楼里所有人"，`/0` = "全世界所有人"。数字越小覆盖范围越大，数字越大（最大32）覆盖范围越小，直到 `/32` 精确到单个 IP。

理解了 `/24` 的原理后，安全组/bucket policy 里常见的 `0.0.0.0/0`、某个具体 IP 后面加 `/32` 这类写法就都能顺理成章看懂——本质都是同一套"前 N 位固定、剩下位可变"的二进制匹配逻辑。

## 四、IAM Policy 里 Statement 数组的顺序有影响吗？（以及和 NACL 的关键区别）

**结论：IAM Policy 里 Statement 的上下顺序完全不影响结果。** 这是一个非常容易和其他 AWS 概念混淆的高频考点。

### IAM 的评估逻辑：不是"从上往下找第一个匹配就停"

AWS 评估权限时，把用户/角色身上**所有生效的 policy、所有 Statement 一次性汇总起来**综合判断：

1. **默认隐式拒绝(implicit deny)**——什么都不写，默认不允许
2. 把所有 policy 里的所有 Statement（不管排第几个、不管在哪个 policy 文件里）都拿出来看一遍
3. **只要其中任何一条是 Explicit Deny 且条件匹配 → 直接拒绝**，不管这条 Deny 排第一条还是最后一条
4. 没有 Deny 匹配，但至少有一条 Allow 匹配 → 允许
5. 都没匹配 → 落回默认隐式拒绝

所以本笔记「二」那道题的 Policy，就算把 Allow 和 Deny 两条 Statement 的上下顺序对调，结果完全一样——因为评估时不是"按顺序读、读到第一条符合的就拿它的结果"，而是"汇总所有条款，只要有一条 Deny 命中就整体判负"。

### IAM Policy / Security Group / NACL 顺序是否重要，三者对比

| | 顺序是否重要 | 评估逻辑 |
|---|---|---|
| **IAM Policy** | **不重要** | 汇总所有 Allow/Deny，Deny 优先，和顺序无关 |
| **Security Group(安全组)** | 不重要 | 只有 Allow 规则，没有 Deny，所有匹配规则汇总生效（求并集），不存在顺序冲突 |
| **Network ACL(NACL)** | **重要！** | **按规则编号从小到大依次检查，第一条匹配的规则（不管 Allow 还是 Deny）立即生效，后面规则不再看** |

**NACL 是唯一"顺序真的会影响结果"的一个**——比如 NACL 规则 100 号写"Deny 全部"，规则 200 号写"Allow 某个 IP"，这个 IP 的流量先匹配到 100 号规则就直接被拒绝，200 号规则根本不会被看到。这也是为什么 NACL 规则编号通常故意留间隔（100、200、300……），方便以后插入新规则又不破坏顺序逻辑。

### 深层原因：为什么 IAM/SG 不需要顺序，NACL 却需要？

**1. IAM Policy 天生要"合并多份独立文件"，根本没有自然顺序可言**

一个 IAM 用户的权限，通常来自好几个独立来源同时叠加：直接挂在用户身上的 inline policy、通过用户组继承的 policy、AWS 托管 policy、customer managed policy，甚至组织层面的 SCP。这些是**分别独立的文件**，相互之间不存在"谁排第一、谁排第二"的关系。既然天然没有顺序可言，评估逻辑就必须设计成"跟顺序无关"——用"只要有一条 Deny 就整体拒绝"，才能在"多份互不相干文件叠加"的场景下得出确定、可预测的结果。这是唯一说得通的设计，本质上体现的是 IAM **安全优先(deny-by-default)** 的设计原则，不是靠顺序取巧的"严格"。

**2. NACL 天生是"单一有序规则列表"，继承自传统网络设备的设计范式**

NACL 本质上模仿的是传统路由器/防火墙的访问控制列表（如思科设备 ACL、Linux iptables），这类设备几十年的标准做法就是：规则写在一张有编号的表里，数据包进来后按编号从小到大依次比对，第一条命中的规则立即生效，后面不再看。NACL 出现的概念比 AWS IAM 更早、更贴近传统网络设备惯例，AWS 只是把这套"传统防火墙规则表"模式搬到云上——它天生是"一张表、一个顺序"，不是"多份文件合并"，自然沿用了"顺序优先、第一条命中就生效"的经典设计。

**3. Security Group 为什么也不需要顺序？**

因为 Security Group **只有 Allow，没有 Deny**——所有匹配的规则都是"允许"，汇总起来求并集即可，不存在"两条规则结果冲突、需要靠顺序决定听谁的"情况，自然不需要排序。

### 一句话总结

- **IAM Policy**：要合并多份互不相干的独立文件，无自然顺序可言 → 设计成"Deny 优先，顺序无关"
- **Security Group**：规则里只有 Allow，没有互相冲突的可能 → 也不需要顺序
- **NACL**：继承自传统网络设备"单一有序规则表"的历史范式，且同时支持 Allow 和 Deny，需要明确先后关系来解决冲突 → 保留"编号顺序、第一条命中生效"的设计

## 五、为什么 AWS 托管策略（如 AmazonS3ReadOnlyAccess）会存在？为什么 Security Group 只有 Allow？

### 为什么 AWS 要提供 `AmazonS3ReadOnlyAccess` 这类"托管策略(Managed Policy)"

核心目的：**把最常见的权限组合预先写好、由 AWS 官方维护，用户不用每次都自己手写 JSON**。

1. **降低重复劳动和出错风险**：很多场景都有"只读 S3、不需要写"这种通用需求（数据分析师、QA账号、只读监控服务），AWS 直接提供一份官方验证过、语法正确、覆盖全面的现成策略，直接挂上即可用，不用每家公司都各自造轮子还容易造错。
2. **AWS 会持续维护更新**：S3 API 不断新增操作（新存储类型、新功能对应的新 Action），AWS 托管策略会由 AWS 官方跟着 API 演进自动更新版本，用户不需要自己盯着补充。自己手写的 policy 没有这个"自动跟进"的便利。
3. **体现"最小权限原则"的最佳实践**：`AmazonS3ReadOnlyAccess` 明确只给 `s3:Get*`、`s3:List*` 这类只读操作，不给 `s3:Put*`/`s3:Delete*`，是 AWS 把"常见安全最佳实践"封装成现成模板，减少企业因图省事直接给 `s3:*` 而埋下的安全隐患。

一句话：AWS 托管策略 = 官方提供的"常见权限组合模板库"。

### 为什么 Security Group 设计成"只有 Allow，没有 Deny"

背后是"默认全部拒绝 + 白名单式放行"的思路，专门针对"单个实例/网卡的门卫"这个场景做了简化：

1. **Security Group 本身默认就是全拒绝的**，不需要 Deny 规则来补充说明"其他都不让进"——初始状态已经是"什么都不允许"，写的每条规则都是往这个全封闭基础上开一个口子。既然默认已经全拒绝，就只需要"允许什么"，不需要"拒绝什么"这个反向操作。
2. **Security Group 是有状态(stateful)的**（详见下方"有状态 vs 无状态"），这让"只留 Allow"更自然——入站被允许后，对应的回程流量自动放行，不需要额外写出站规则。如果同时还要支持 Deny 且要考虑顺序优先级，会让"入站被允许但出站又被某条 Deny 拦住"这类自相矛盾的情况变得复杂。只保留 Allow，模型更简单直观、不会自相矛盾。
3. **"精细拦截/黑名单"这种需求，AWS 特意留给了 NACL 去做**：需要"专门拒绝某个具体坏 IP，即使其他规则允许它"，正是 NACL 存在的意义。AWS 有意把"实例级别、有状态、只允许、简单直观"(Security Group)和"子网级别、无状态、支持顺序化 Allow+Deny、更强大也更复杂"(NACL)拆成两层，做**纵深防御(defense-in-depth)**：多数场景用简单的 Security Group 白名单就够，少数需要精细黑名单/顺序控制的场景再上 NACL 兜底。

### "有状态(Stateful)"到底是什么意思

**有状态 = 系统会自动记住/追踪一次网络连接的来龙去脉，一旦这次连接的"去程"被允许，对应的"回程"会被自动放行，不需要再单独写一条规则。**

具体场景：EC2 的 Security Group 只写了一条 Inbound 规则——允许 TCP 80 端口(HTTP)、来源任意 IP。

1. 用户电脑 → EC2:80 发起请求（去程）→ 匹配"允许入站80端口" → 放行
2. EC2 处理完要把网页内容返回给用户（回程，方向是出站/outbound）——**因为 Security Group 有状态，会自动记住"刚才这个连接是我允许进来的"**，所以这个回程数据会被自动放行，即使你压根没在 Outbound 规则里写过"允许80端口出站"。

**对比：NACL 是无状态(Stateless)的**——完全不记得"这个流量之前发生过什么"，入站和出站是两件互相独立、必须分别写规则的事。同样的场景用 NACL 控制：必须手动写一条 Inbound 规则（允许80端口进来），**还必须再手动写一条 Outbound 规则**（允许回程用的临时端口/ephemeral port，通常 1024-65535 范围）出去——少写一条，这个连接就会失败（请求能进来，但响应发不出去，用户看到超时）。

**一句话总结**：
- **有状态(Stateful，Security Group)** = "记得住来龙去脉"：去程被允许，回程自动放行，不用操心。
- **无状态(Stateless，NACL)** = "每次都失忆"：入站、出站是两码事，必须分别显式写规则，漏写回程规则流量就会被卡住。

这也是为什么 Security Group"只需要 Allow"会显得更自然——有状态机制帮你把"双向打通"这件事自动处理掉了；而 NACL 因为无状态、且支持 Allow+Deny 顺序判断，天生更复杂，但也更适合做"顺序化的精细拦截"。
