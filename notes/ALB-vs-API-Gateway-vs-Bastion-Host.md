# ALB vs API Gateway vs 堡垒机（Bastion Host）网络层笔记

## 一、Lambda Alias 算不算负载均衡？为什么还需要 ALB？

使用 Lambda Alias 时，Lambda 服务的控制平面确实充当了"版本间代码调用路由器"，但它**绝对无法替代 ALB**。两者处于完全不同的网络层级：

- **Lambda Alias 只是"代码版本选择器"**：不具备任何七层网络代理功能，既不能处理 HTTP 报文、解密 SSL 证书，也不能把流量导向 Lambda 以外的任何地方（比如不能导给 EC2 或 ECS）。
- **ALB（应用负载均衡器）是"七层网络网关"**：负责把公网的 HTTP/HTTPS 流量安全接进来。

### 为什么 ALB 依然不可替代？

1. **跨服务统一路由**：ALB 可以把 `/user` 路由给 ECS 容器，把 `/pay` 路由给 EC2，把 `/report` 路由给 Lambda。Lambda Alias 只能在自己的 Version 1 和 Version 2 之间互转。
2. **高级网络与安全特性**：ALB 支持挂载 AWS WAF（Web 应用防火墙）、域名 TLS/SSL 证书卸载、HTTP/2、WebSocket 长连接以及固定公网 IP。Lambda Alias 根本不知道什么是 HTTP 协议。
3. **流量入口**：Lambda 默认没有公网 IP 和端口。外部用户要访问 Lambda，前面必须挂一个 **ALB** 或 **API Gateway** 来接收网络请求。

## 二、ALB 和堡垒机（Bastion Host）经常放在一起吗？

**在网络拓扑上，它们是"隔壁邻居"；但在功能职责上，完全不打交道。**

在标准的企业级 AWS VPC 架构（三层子网）中，两者通常一起出现在 **Public Subnet（公网子网）** 里，扮演守门的"一文一武"：

- **ALB（业务流量门卫 - "文官"）**：面向**终端用户**。只接收公网的 80/443 HTTP 业务请求，转发到 Private Subnet（私有子网）里的应用服务器（EC2/ECS/Lambda）。
- **堡垒机（运维管理门卫 - "武官"）**：面向**内部开发与运维人员**。私有子网里的数据库（RDS）和服务器禁止公网直连，运维人员必须先 SSH（22 端口）连上公网子网里的堡垒机，再以堡垒机为跳板安全登录到内网服务器进行维护。

ALB 负责管"业务客流"，堡垒机负责管"内部修缮"，两者共同构成私有子网与公网隔离的第一道防线。

## 三、ALB vs API Gateway：为什么不合并成一个服务？

把 API Gateway 和 ALB 拆开，是典型的"高吞吐网络转发"与"复杂 API 业务管理"在软件工程上的解耦。如果强行合并，要么负载均衡器因加载太多复杂逻辑而**变慢变贵**，要么 API 网关因追求极致网络吞吐而**丧失灵活性**。

### 核心差异对照

| 维度 | ALB（应用负载均衡器） | API Gateway（API 网关） |
|---|---|---|
| **形象比喻** | **高速公路收费站**（只查车牌、快速放行） | **机场安检与海关处**（查护照、测体温、限流、填表格） |
| **核心职责** | 流量分发、健康检查、高并发传输 | API 生命周期管理、鉴权、限流、请求转换 |
| **处理延迟** | **极低（< 5 毫秒）** | 较高（~10–30 毫秒，因为要执行复杂逻辑） |
| **计费模式** | 按固定小时费 + 极便宜的数据处理费 | 按**请求调用次数**计费（大规模流量下单价显著高于 ALB） |
| **典型后端** | EC2 实例、ECS 容器、IP 地址 | Lambda 函数、AWS 服务（如 S3/SQS）、任意 HTTP 接口 |

"典型后端"是指位于 ALB 身后、真正接收并处理请求的计算资源——只要能提供网络 IP 地址和端口（IP:Port）、能接收并响应 HTTP/TCP 协议的实体，就是 ALB 的后端（EC2 实例、ECS 容器任务或 IP 列表）。

### 不合并的 3 个核心原因

1. **性能与延迟的物理矛盾**：ALB 的目标是处理海量数据吞吐，单机每秒处理几万个 HTTP 请求，底层代码必须极致精简（仅做 TCP/HTTP 头部的基础路由）。如果让 ALB 在转发流量前去解析 JWT Token、针对不同 API Key 算 Rate-Limit、修改 JSON 请求体，转发延迟会瞬间翻倍，主干网络吞吐量会急剧下降。
2. **成本模型的巨大悬殊**：ALB 极度便宜——处理 1000 万次请求可能只需几美分，非常适合视频流、长连接（WebSocket）、海量静态资源或容器微服务。API Gateway 卖的是"功能"——1000 万次 REST API 请求约需 35 美元；如果系统有大量纯转发的高频流量，强行走 API Gateway 会让账单爆炸。
3. **架构解耦：直连 AWS 服务能力**：API Gateway 具备一个 ALB 完全不具备的超能力——**无需任何计算层（Lambda/EC2），直接向 AWS 服务读写数据**。例如前端可以直接发请求给 API Gateway，自动把数据推入 SQS 队列或写入 DynamoDB。而 ALB 离开后面的 EC2/ECS/Lambda 就完全无法工作。

### 为什么 ALB 必须挂 EC2/ECS/Lambda，而不能像 Gateway 一样直连 S3/SQS？

源于两者在底层设计哲学上的根本差异：

- **ALB 是"纯粹的高速网络管道（网络代理）"**：底层代码完全为极致的 TCP/HTTP 数据包转发优化（类似 Nginx/Envoy），只懂得按网络协议原封不动地透传数据。它不懂 AWS 的内部专用协议（不懂 IAM 签名认证，也不懂 S3/SQS 的底层 API 结构），必须有一个能监听端口的真实计算服务（EC2/ECS/Lambda）来接管这个 HTTP 请求。
- **API Gateway 是"内置 AWS SDK 的智能引擎"**：内部搭载协议转换与 AWS 引擎。配置直连 S3/SQS 时，API Gateway 收到公网 HTTP 请求的瞬间，会在内部把它直接翻译成 AWS SDK 的 API 调用（如 `S3:PutObject` 或 `SQS:SendMessage`），完成身份签名与数据映射。

如果把 API Gateway 这套繁重的翻译逻辑塞进 ALB，ALB 就再也无法保持"每秒处理几十万高并发数据包、延迟只有几毫秒、且价格极度便宜"的性能优势。

### 实际架构中的协作模式

在大型企业级架构中，两者非但不冲突，反而经常配合使用：

```
客户端 → API Gateway（负责 Token 校验、防刷限流、统一 API 域名）
       → ALB（负责内网的高并发低延迟分发）
       → ECS 容器集群
```

- 需要**极致性能、高吞吐、低成本** → 直接用 **ALB**。
- 需要**精细化 API 治理、开发者平台、Serverless 配合** → 必须用 **API Gateway**。

## 四、ALB 的健康检查

ALB 的"健康检查"相当于给服务器戴的"心率监测仪"：每隔几秒钟（如 5 秒）向后端每台服务器发送一个请求（比如 GET `/health`）。如果某台服务器连续几次没有返回 `200 OK`（进程卡死、内存爆了、甚至服务器直接宕机），ALB 会立刻将其标记为"不健康"，停止把新流量发给它，直到恢复正常。

这无法只靠 API 自己管理——如果服务器硬件崩溃或容器死锁，API 代码根本连运行的机会都没有，自然无法对外报告自己的状态。必须由站在前面的 ALB 来做这个外部监督者。

## 五、ALB 与 API Gateway 在现代 AWS 架构中的地位：两大生态的绝对核心（Top Tier）

只要一家公司在 AWS 上部署了 Web 网站、手机 App 后端，或任何对外提供网络接口的系统，几乎 100% 绕不开这两个服务中的一个（甚至两个一起用）。它们各自统治着 AWS 的两大技术生态。

### 1. ALB —— "容器与传统架构的霸主"

- **出场率**：极高。
- **统治领域**：几乎所有基于 ECS/Kubernetes（EKS）的现代容器微服务，以及基于 EC2 的传统架构，公网"大门"全都是 ALB。
- **为什么不可或缺**：只要有超过一台以上的服务器/容器，就必须有东西把用户请求均匀分发下去（否则流量全砸在一台机器上就宕机），ALB 就是这个"高速枢纽"——便宜、稳定、能抗几百万并发。

### 2. API Gateway —— "Serverless（无服务器）架构的霸主"

- **出场率**：极高（且在不断上升）。
- **统治领域**：只要企业用 Lambda 写 API 后端，或需要把自己的 API 作为商品开放给第三方调用（开放平台），就必定会用 API Gateway。
- **为什么不可或缺**：对外提供标准 API 接口，需要防黑客刷接口（限流）、验证用户 Token（鉴权）、针对不同客户分发不同 API Key（甚至按调用次数收钱）。这些功能自己写代码实现会非常痛苦，API Gateway 全都做好了，开箱即用。

### 同框合作的经典架构

很多大厂的经典架构：

```
用户 APP → API Gateway（第一道安检：校验 JWT Token、防恶意刷量）
         → ALB（内网的高速流量分发）
         → 后端成百上千个微服务容器（ECS）
```

**总结**：ALB 是物理层面的流量搬运工，API Gateway 是业务层面的 API 大管家。在日常开发和 SAA 考试中，两者都是"必考题"和"必修课"——理解了它俩，基本就理解了整个 AWS 流量入口的核心逻辑。

## 六、Lambda 是否必须搭配 API Gateway？为什么 AWS 不直接用 Nginx 而要单独发明 ALB？

Lambda 并不是"绝对只能"配合 API Gateway（现在有 **Function URL**），但要构建商业级 Web 后端它依然是标准解法；AWS 推出 ALB 是为了实现无服务器化的完全托管；针对第三方 API 场景，API Gateway 提供的商业化管控与计费能力则是传统 Load Balancer 根本不具备的。

### 1. 为啥 Lambda 写后端经常要用 API Gateway？

Lambda 本身只是一段代码，没有"网络网卡"去监听 80/443 端口。

- **本质是"HTTP 协议翻译官"**：Lambda 默认只能通过 AWS 内部命令（如 `Invoke`）触发，不懂什么是 HTTP 请求、Cookie、URL 路径。API Gateway 站在公网上接收 HTTP 请求，翻译成 Lambda 能读懂的 JSON 事件（Event），再把 Lambda 返回的 JSON 包装成 HTTP 响应吐回浏览器。
- **虽有替代方案，但 API Gateway 更全面**：Lambda 也可以直接开启 **Function URL**（直接给 Lambda 一个 HTTP 地址），或挂在 ALB 后面。但需要复杂的 API 路由分发、Token 身份校验、防刷限流时，API Gateway + Lambda 依然是功能最完备的组合。

### 2. 为啥 AWS 不直接用 Nginx，而要单独发明 ALB？

Nginx 是"需要你自己运维的软件"，ALB 是"开箱即用、无需运维的云服务"。

自建 Nginx 做负载均衡要面临的运维难题：

- **单点故障与扩容**：得自己租至少两台跨可用区（Multi-AZ）EC2 跑 Nginx；Nginx 所在 EC2 挂了怎么办？流量暴涨 CPU 满了怎么办？得自己配置 Keepalived 做主备，写脚本做弹性扩容。
- **证书与生态对接**：SSL 证书到期要手动更换，后端 ECS 容器扩缩容了要手写配置文件去 `nginx -s reload`。

ALB 的目的就是把 Nginx"云原生化"：底层可能也借鉴了 Envoy/Nginx 等技术，但对用户而言是完全托管的服务——不需要管它跑在几台机器上，天生跨多可用区高可用，自动根据流量无限缩放，免费自动续期 HTTPS 证书，并能实时与 AWS Auto Scaling、ECS 容器增减动态联动。**买的是"服务"，而不是"运行 Nginx 的虚拟机"**。

### 3. 为啥给第三方开放 API，就必须要用 API Gateway？

面向第三方（B2B/开放平台）开放 API 时，核心需求不再是单纯的"流量转发"，而是"**API 商业化管控**"——靠自己写代码或普通负载均衡器实现，成本极高：

- **按客户计费与配额管理（Usage Plans & API Keys）**：可给不同第三方分配不同 API Key，设置 A 客户每月限流 10,000 次、B 客户每秒限流 50 次。一旦超量，API Gateway 在网关层直接弹回 `429 Too Many Requests`，超量流量根本不会打进后端，也不消耗算力。
- **开发者文档与 SDK 一键生成**：可直接导出标准 OpenAPI（Swagger）规范文档，甚至一键生成 Java/Python/JavaScript 客户端 SDK，直接给第三方开发者使用。
- **API 生命周期与版本管理（Stages）**：方便管理 `/v1/` 和 `/v2/` 版本的灰度发布与废弃，保障第三方接续的稳定性。

## 七、ALB 如何实现灰度发布（Canary）？

Nginx 是一套开源软件，在 EC2 上自建确实既贵又麻烦；而 ALB 完全可以实现灰度发布，这正是它的核心强项之一。

**为什么 Nginx 放在 EC2 上又贵又低效？**

- **软件 vs 云服务**：Nginx 就像 MySQL 或 Redis，是需要宿主机的软件。要在 EC2 上跑 Nginx，为防止单点故障，至少需要购买两台跨可用区（Multi-AZ）的 EC2 实例，并配置负载均衡和运维脚本。机器租金 + 人力运维成本极高。
- **ALB 本质就是"AWS 帮你自己搭建并运维好的 Nginx 集群"**：AWS 正是为解决用户自建 Nginx 的痛点才推出 ALB。不需要购买任何 EC2 机器，直接按流量和基础服务付费，省去底层服务器的硬件开销与运维麻烦。

**ALB 灰度发布的底层机制：加权目标组路由（Weighted Target Groups）**

1. **建立新旧两个目标组（Target Groups）**：`Target Group A` 包含跑着老代码 V1 的 10 个容器/实例；`Target Group B` 包含跑着新代码 V2 的 2 个新容器/实例。
2. **在 ALB 配置流量权重**：路由规则中将 `Target Group A` 权重设为 90，`Target Group B` 权重设为 10。
3. **网络层按比例分发**：ALB 接收公网请求时，自动把 10% 的 HTTP 流量路由到 B（新版本），90% 留给 A（旧版本）。
4. **自动化调权与回滚**：配合 AWS CodeDeploy 或 ArgoCD 等部署工具，ALB 会盯着那 10% 流量。如果没有引发报警，工具自动将权重从 `90:10` 逐步调整为 `50:50` 直至 `0:100`；一旦发现异常，瞬间将权重调回 `100:0` 完成无感回滚。

## 八、现实中 ALB 做蓝绿/金丝雀发布的覆盖面远高于 API Gateway

### 三个核心原因

1. **企业底层架构的占比决定（容器/VM 占绝对主流）**：工业界 70%~80% 以上企业核心业务运行在容器（ECS/EKS/Kubernetes）或 EC2 上。ALB 作为这些服务的标准公网/内网入口，内置的"加权目标组（Weighted Target Groups）"是目前实现容器蓝绿部署最成熟、成本最低的标准解法。
2. **分工明确：把流量切分交给"数据面"**：在"API Gateway + ALB + 后端服务"的标准大厂架构中，API Gateway 的职责严格限制在安全鉴权、限流和防刷上；具体的版本切换、高并发流量路由等"数据面重活"，全权交给延迟极低且计费便宜的 ALB 处理。
3. **Serverless 场景下 API Gateway 的职责被下沉**：即便是完全基于 Lambda 的 Serverless 架构，开发者也更倾向于直接用 **Lambda Alias（别名权重）** 配合 CodeDeploy 做蓝绿发布，而不是在 API Gateway 的 Stage 层配置繁琐的灰度规则（对应第五节笔记中 Lambda Alias 加权路由的机制）。

### 现实中的分工场景

- **用 ALB 做蓝绿（日常 90% 的情况）**：后端服务（ECS/EC2）更新了新版本代码，需要从老集群（Blue）无感切到新集群（Green）。
- **用 API Gateway 做蓝绿（极少数情况）**：涉及 API 协议突破性变更（如 `/v1` 大版本升级到 `/v2`），或需要根据请求头中的特定字段（比如 `Header: Beta-User`）定向路由到测试环境。

## 九、ACM 证书：AWS 官方免费 SSL/TLS 证书

**ACM（AWS Certificate Manager）证书**是 AWS 官方提供的免费 SSL/TLS 数字证书，专门用来给域名和网站开启 HTTPS 加密访问（让浏览器地址栏出现"小锁"图标）。

### ACM 证书的 3 大核心优势

- **完全免费（0 成本）**：只要将 ACM 证书挂载在 AWS 的托管服务（如 ALB、CloudFront、API Gateway）上，申请和续期完全不收一分钱。
- **全自动续期（告警救星）**：传统 SSL 证书（如 Let's Encrypt 或付费证书）通常 90 天或 1 年失效，忘记手动替换会导致网站服务直接瘫痪。ACM 只要绑定在 AWS 资源上，AWS 会在过期前全自动静默续期，无需任何人工干预。
- **零私钥泄露风险**：不需要像传统服务器那样下载 `.crt` 或 `.key` 文件再手动上传。证书在 AWS 内部生成并保管，部署时只需在下拉菜单里勾选，即可一键绑定到 ALB 或 CloudFront 上。

### 最常见的 3 个使用场景

- **CloudFront + S3 静态网站**：给自定义域名（如 `https://www.yourdomain.com`）开启 HTTPS（对应 [S3-CloudFront-Migration-Concepts.md](S3-CloudFront-Migration-Concepts.md) 第三节"viewer TLS 证书为什么必须在 us-east-1"）。
- **ALB 负载均衡（TLS 卸载）**：公网流量通过 HTTPS（443 端口）安全打到 ALB，ACM 证书在 ALB 处完成解密（TLS Termination），再以 HTTP 转发给内网的 ECS 或 EC2，减轻后端服务器的加密计算开销（详见第十节）。
- **API Gateway 自定义域名**：为暴露给前端或第三方的 API 绑定高可信度的 HTTPS 接口域名（如 `https://api.yourdomain.com`）。

### 免费证书 vs 付费证书：绝大多数情况下完全不需要花钱

无论使用云厂商服务还是自建服务器，目前主流的 **DV（域名验证型）** HTTPS 证书已全面免费化。

| 维度 | 免费证书（DV 域名验证型） | 付费证书（OV/EV 组织与企业验证型） |
|---|---|---|
| **适合场景** | **99% 的网站、App、API、个人与企业项目** | 金融银行、大型电商、对企业资质合规有硬性要求的场景 |
| **安全强度** | 极高（与付费证书采用相同的非对称加密算法） | 极高（加密强度完全相同） |
| **验证内容** | 仅验证是否拥有该域名的控制权 | 审核企业营业执照、法人身份、电话真实性等 |
| **浏览器显示** | 显示"小锁"图标，点开显示域名已安全加密 | 点开证书可明确查看"企业真实官方名称" |
| **代表来源** | AWS ACM、Let's Encrypt、Cloudflare | DigiCert、Sectigo、GlobalSign |

**常用的 3 大免费 HTTPS 方案**：

- **AWS 托管场景（AWS ACM）**：0 元。挂载在 ALB、CloudFront、API Gateway 上完全免费，支持无限次全自动静默续期。
- **自建服务器场景（Let's Encrypt）**：0 元。通过 `certbot` 自动化工具，几条命令即可免费申请并在 Nginx/Apache 上安装，支持自动脚本续期。
- **CDN / 域名托管场景（Cloudflare）**：0 元。将域名 DNS 接入 Cloudflare，直接开启"一键免费 HTTPS"。

**什么情况下才不得不花钱？**

- **企业合规与资质背书**：金融机构或大厂为满足安全合规审计，需要在证书详情中展示企业官方全称（OV/EV 证书）。
- **品牌与法律赔付保障**：付费证书附带防伪造保险赔付金额（如最高 150 万美元赔付），且某些传统大企项目招投标合同中明确要求必须采购品牌商业证书。
- **极特殊旧设备兼容**：极个别古老的嵌入式设备或老旧系统，内部预置的根证书库不信任 Let's Encrypt 等新型免费根证书，需要购买历史悠久的老牌商业根证书。

正常做系统开发、部署网站或 API，直接用 **AWS ACM** 或 **Let's Encrypt** 即可，一分钱都不用花。

## 十、为什么要在 ALB/网关层做 TLS 卸载（TLS Termination）？

将 TLS 在 ALB 或网关层面解密（**TLS 卸载 / TLS Termination**），核心是为了释放后端服务器算力、简化证书运维，以及让负载均衡器有能力"拆包"进行高级流量治理。

### 1. 算力解脱：把 CPU 留给业务代码

HTTPS 的 TLS 握手与加解密是高度消耗 CPU 的"计算密集型"数学任务。如果让后端成百上千个应用容器（Java、Python、Go）直接处理解密，大量算力会浪费在加解密上。把解密工作交给带硬件加速的 ALB 或网关，后端应用服务器就能 100% 专注跑业务逻辑。

### 2. 统一证书管理：避免配置噩梦

如果坚持"端到端全程 HTTPS"，就需要在后端每一个容器或 EC2 上都安装、配置并定期更换证书，机器规模变大后运维成本极高。采用 TLS 卸载后，只需在 ALB 上挂载一张 ACM 证书即可，更新时全自动静默完成，后端服务完全不需要感知证书的存在。

### 3. 必须"拆开信封"才能做七层路由与安全防御

未解密的 HTTPS 报文对 ALB 来说是完全不可见的"黑盒"。只有卸载了 TLS，ALB 和安全组件才能透视 HTTP 报文的明文内容：

- **按路径路由**：查看 URL（例如把 `/user` 导向用户微服务，`/pay` 导向支付微服务）。
- **应用安全（WAF）**：检查请求 Body 和 Header 中是否包含 SQL 注入或 XSS 攻击代码。
- **会话保持（Sticky Session）**：读取 Cookie 确保同一用户的后续请求打到同一台服务器。

### 4. 内网 VPC 物理隔离：安全与性能兼顾

公网环境（用户 → ALB）充满监听与黑客攻击，必须使用 HTTPS 强加密；而内网环境（ALB → 私有子网中的 ECS/EC2）跑在 AWS 物理隔离的 VPC 私有网络里，公网根本无法触及。在安全的内网中使用纯 HTTP 传输，既能保证合规安全，又消除了内网节点间互相加密的性能开销。

> 注：在金融、医疗等极高安全合规要求（**零信任架构 Zero-Trust**）的场景下，内网 ALB 到后端也会强制重新加密，但这属于牺牲部分性能换取绝对合规的特例。
