# RDS Proxy / ElastiCache / Read Replica / SQS 与 S3 访问控制笔记

## 一、Lambda + Aurora 升级期间数据丢失问题

### 题目场景
API Gateway → Lambda → Aurora MySQL。每次公司升级数据库时，Lambda 在升级期间连不上数据库，导致这段时间的客户数据没有被记录下来。要求：设计方案确保升级期间产生的数据不丢失。

### 正确答案：SQS FIFO 队列 + 轮询 Lambda
把"接收数据"和"写入数据库"两个动作解耦：
- API 触发的 Lambda 只负责把客户数据丢进 SQS FIFO 队列（这一步不依赖数据库是否可用）
- 另一个 Lambda 专门轮询队列，数据库恢复可用后再把消息取出来写入 Aurora
- 消息在队列里可以放着等（最长 14 天），数据库不可用的这段时间数据不会丢，只是延迟写入
- FIFO 保证同一 key 内消息顺序，适合有顺序要求的场景

### 为什么不是 RDS Proxy
RDS Proxy 只是 **连接池中间件**，作用是复用 TCP 连接、加速 failover 切换，**它不存储/缓冲任何业务数据**。数据库真的完全不可达时（比如升级窗口内的重启/切换），Proxy 只是把这次请求转发失败，不会把这条没发出去的 INSERT 存起来等数据库恢复了再补发——它没有"先存后发"的能力。这是本题最大的陷阱：把"连接管理"和"数据持久化/缓冲"这两个完全不同层次的问题搞混。

## 二、RDS Proxy 到底是什么、解决什么问题

### 是什么
RDS Proxy 是 AWS 全托管的**数据库连接池中间件**，本质类似开源的 PgBouncer（PostgreSQL）/ ProxySQL（MySQL）——如果不用 AWS，传统部署一般就是自己搭这两个开源组件来实现同样的连接池功能。

对客户端而言，RDS Proxy **伪装成一台标准的 MySQL/PostgreSQL 服务器**，监听同样的协议（wire protocol）。应用代码 / MySQL driver 完全不需要改，只需要把连接字符串里的 endpoint 从数据库地址换成 Proxy 地址——这就是"透明"的含义。

### 解决的三个问题
1. **连接数暴增**：Lambda 并发一高（尤其是大量 cold start 同时发生），每个执行环境都要新建一条到数据库的 TCP 连接，容易把数据库的 `max_connections` 打爆。Proxy 让大量 Lambda 共享一小批已经建立好、已完成认证的真实连接，请求在 Proxy 内部排队复用这些连接（这是 Proxy 自己的调度逻辑，应用代码不用写任何排队/连接管理代码）。
2. **Aurora failover 重连变慢**：writer（唯一能处理写操作的主节点）故障切换后，客户端通常要等 DNS TTL 才能感知新 writer 地址，RDS Proxy 能更快地把流量切到新 writer。
3. **凭证管理**：可以配合 Secrets Manager 做数据库账号密码轮换。

### 为什么不能靠"把 max_connections 调大"来替代
- 每个数据库连接在服务端都要占用真实的内存/CPU（会话状态、缓冲区等），连接数调太大容易把数据库内存吃满导致 OOM，或者让 CPU 花大量时间在进程/线程调度(context switch)上，反而挤占了原本用来跑查询的资源和缓存(buffer pool)空间。
- Lambda 的并发是脉冲式暴涨，不是稳定值，"调多大才够"永远猜不准，本质是治标不治本。
- Failover 场景下连接数上限完全没用，问题是"如何更快知道新 writer 地址并重连"，跟连接池大小无关。

### 覆盖的数据库引擎
RDS Proxy 支持 MySQL、PostgreSQL、MariaDB（以及后来加入的 SQL Server），**不支持 Oracle** 等其他引擎——SAA 做题时如果题目背景是 Oracle/SQL Server 等，要留意 RDS Proxy 可能不是有效选项。

### RDS Proxy vs ElastiCache（Redis）—— 不是同一类东西
| | RDS Proxy | ElastiCache（Redis/Memcached） |
|---|---|---|
| 作用对象 | **连接**（复用 TCP 连接） | **数据**（缓存查询结果） |
| 是否需要改应用代码 | 不需要，换个 endpoint 即可 | 需要，应用要显式写"先查缓存，未命中再查库，再写回缓存"的逻辑 |
| 会不会替数据库挡掉查询压力 | 不会，请求最终还是打到 DB 上执行 | 会，命中缓存就不用查数据库 |

两者解决的瓶颈完全不同，实际架构里经常一起用（Redis 缓存热数据 + RDS Proxy 管理连接）。

## 三、ElastiCache 相关概念

### 是什么
AWS 全托管的内存缓存服务，底层引擎二选一：**Redis**（2009年发明，功能丰富：多种数据结构、支持持久化、支持主从复制/高可用，现实中用得更多）或 **Memcached**（2003年发明，只支持简单 key-value，不支持持久化和复制，原生多线程）。

"全托管"的价值在于：AWS 帮你处理节点故障自动 failover、自动打补丁、自动备份、CloudWatch 监控集成——如果自己在 EC2 上裸装 Redis，这些运维工作（高可用配置、打补丁、监控告警、备份恢复）全部要自己做。ElastiCache 内部跑的就是真正的 Redis/Memcached 引擎，可以用标准 client 连接，区别只是"谁来运维"。

### 典型使用模式（cache-aside）
```
应用要读数据 → 先查缓存
  → 命中(hit)：直接返回，不碰数据库
  → 未命中(miss)：查数据库 → 拿到结果 → 顺便写一份到缓存 → 返回给应用
```

### 持久化（Persistence）
Redis 本质是内存数据库，数据平时都在 RAM 里，进程崩溃/机器重启数据会全部消失（内存是易失性存储）。Redis 提供两种持久化机制把数据备份到磁盘：
- **RDB**：定期把内存数据整体做一次快照写入磁盘
- **AOF**：把每条写命令实时追加写入日志文件，重启后重放这些命令重建数据

普通关系型数据库（RDS/MySQL/PostgreSQL）默认就是持久化的（写入即落盘）；Redis 的持久化是可选功能，纯当缓存用时（丢了可以从数据库重新捞）很多场景选择不开。

### 分布式锁（Distributed Lock）
在多台机器/多个进程之间协调"同一时刻只能有一个人做某件事"的机制。例如多台服务器同时跑同一个定时任务，为避免重复执行，各自尝试向 Redis 写入同一个 key（利用"仅当 key 不存在时才写入成功"的原子操作），第一个写入成功的机器才真正执行任务，其他机器放弃。之所以叫"分布式"，是因为语言内置的锁（如 Java synchronized）只能协调同一进程内的线程，跨机器协调必须靠 Redis 这类共享中间存储。

### 主从复制（Master-Slave / Primary-Replica Replication）
一个 Master 节点负责所有写操作，一个或多个 Slave/Replica 节点从 Master 同步数据、只处理读请求。Master 自身也能读，只是"写"这个动作只能发生在 Master 上。数据是各自维护一份拷贝、通过日志同步近实时保持一致（不是共享同一份存储），因此 Replica 的数据会有轻微复制延迟（replication lag），属于最终一致性。Replica 还可以在 Master 故障时被提升(promote)为新的 Master，兼顾"读写分离"和"高可用"两个用途。这个概念不是 Redis 独有，MySQL/PostgreSQL/MongoDB 等都有类似机制，对应到 RDS 就是下面的 Read Replica。

### 自动/手动维护窗口
"窗口"指允许系统对实例做维护操作（打补丁、小版本升级）的一段时间范围：
- **自动窗口**：预先配置好一个时间段（如"每周日凌晨3-4点"），AWS 在这个时间自动打补丁，不用人管，但补丁应用时实例可能短暂重启/中断，通常挑业务低峰期。
- **手动**：某些更新不会自动应用，需要用户自己去控制台点"立即应用"或选时间手动触发，好处是完全掌控升级时机，方便提前验证兼容性。

## 四、Read Replica（读副本）

### 本质
不是"临时复制一个静态文件"，而是**持续、近实时地复制主库的数据变化，生成一个完整独立、可以一直存在、能正常执行 SQL 查询的只读数据库实例**。机制：主库写操作产生事务日志（如 MySQL binlog）→ Read Replica 持续拉取并重放这些日志 → 保持与主库同步（异步复制，通常毫秒到几秒延迟）。Replica 有自己独立的计算资源，读请求打到它身上完全不占用主库资源，但**只能读、不能写**。

### 题目场景：脚本随机跑统计查询拖慢开发团队
SQL 数据库（RDS Single-AZ）被公开访问存电影数据，一个脚本随机跑查询统计新增电影数，开发团队反映跑脚本时数据库性能变差。要求：用**最小运维开销**解决。

**正确答案：创建 Read Replica，让脚本只查 Read Replica**。只需把脚本的连接字符串/endpoint 换成 Read Replica 的地址，代码逻辑、SQL 一行不用改，读流量和开发团队的主库负载彻底隔离。

**为什么不是 ElastiCache**：需要改应用代码加缓存读写逻辑，且这类"统计新增数量"的聚合查询涉及不断变化的数据，缓存命中率/失效策略要额外设计，还要新增部署维护一套缓存集群——运维开销明显比换个 endpoint 高。
**为什么不是 Multi-AZ**：Multi-AZ 的备用实例只是故障转移用的热备，不可读，不能分担读流量。
**为什么不是人工每天导出**：纯人工操作，运维开销最大，不是自动化方案。

### Read Replica 的其他常见场景
1. 跨区域灾备 / 就近访问（降低异地用户读延迟，兼具异地备份）
2. 报表 / BI / 数据分析类重查询，避免拖累生产主库
3. 应急场景下手动提升(promote)为独立可写主库，作为灾难恢复手段
4. 数据库引擎/版本升级前的兼容性验证

### 连接字符串 / Endpoint 概念
Endpoint 是数据库实例对外的网络地址（域名+端口）。连接字符串是应用配置里包含"如何连接数据库"全部信息的一串文本（endpoint + 端口 + 库名 + 用户名密码）。创建 Read Replica 后 AWS 会给它单独生成一个不同的 endpoint，"让脚本查 Replica"具体操作就是换这一个配置项。

### Cold Start / Hot Start（Lambda 相关，连接数暴增的根源）
- **Cold start**：Lambda 执行环境从零初始化（下载代码、启动运行时、跑全局初始化代码如建 DB 连接），有明显延迟，发生在首次调用、并发扩容出新实例、或实例闲置太久被回收后。
- **Hot/warm start**：复用已存在的执行环境（连接等状态都还在），跳过初始化直接执行，延迟低。
流量突增会触发大量并发扩容 → 大量 cold start → 每个新环境都重新建一条数据库连接 → 这是连接数瞬间暴涨、进而需要 RDS Proxy 的根本原因。

## 五、S3 相关考点

### 场景1：降低数据共享的传输成本
Survey 公司在 S3 存 3TB+ 数据，要分享给欧洲 marketing 公司，要求**公司自己的传输成本尽量低**。

**正确答案：开启 Requester Pays**。开启后，下载方（marketing 公司）必须在请求里显式声明愿意付费，这次请求产生的数据传输费用记在请求方账单上，而不是 bucket 所有者（survey 公司）账单上——直接把成本转嫁给下载方。

- **为什么不是跨账号访问（cross-account access）**：只解决"能不能访问"的权限问题，跟"谁付钱"无关。默认情况下不管是不是跨账号访问，数据传输费用都算在 bucket 所有者头上，配置跨账号权限不会自动转嫁费用，无法降低公司自己的成本。
- **为什么不是 CRR（Cross-Region Replication，跨区域复制）**：把 bucket 数据自动异步复制到另一个 Region 的 bucket，本身是持续产生的传输/存储费用，费用由**源 bucket 所有者**承担，会增加而不是降低公司成本，且 3TB 持续增长的数据每次都要重新复制。
- **为什么不是 Intelligent-Tiering + 同步**：Intelligent-Tiering 优化的是存储成本分层，跟"传输给第三方"的费用无关；"同步"本质也是一次数据传输，费用仍算发起方。

### 场景2：防止 S3 文件被意外删除
公开访问的机密审计文档存 S3，已用 bucket policy 做最小权限控制，管理层担心**意外删除**，要求更安全的方案。

**正确答案：开启 Versioning + MFA Delete**。
- Versioning：每次覆盖/删除对象时保留旧版本（删除变成打删除标记，不是真的抹除数据），可随时恢复。
- MFA Delete：在 Versioning 基础上，要永久删除某个版本或关闭 Versioning 本身，必须额外提供 MFA 一次性验证码，仅有 IAM 权限不够，大幅提高误删变成永久丢失数据的门槛。

- **为什么不是给 IAM 用户开 MFA（登录时的 MFA）**：这只是让"登录"这一步更安全，防止账号被盗用；但审计人员正常登录后，一样能正常执行删除操作，不能防止"合法登录的人手滑误删"。
- **为什么不是 KMS 加密并限制访问 KMS key**：KMS 加密解决的是**保密性**（防止未授权的人读取内容），跟"删除"是两码事——即使限制了访问 KMS key 导致对方读不了内容，只要还有 `s3:DeleteObject` 权限，一样能把对象删掉。
- **为什么不是"给 IAM 账户加 Lifecycle policy 在审计期间 deny 删除"**：技术上不成立，S3 Lifecycle policy 是附加在 bucket/对象上、用于自动转换存储类型或过期删除的规则，不能附加在 IAM 账户上、也不能用来按日期 deny 某个 action，这是干扰项。

### MFA（Multi-Factor Authentication，多因素认证）概念
要求至少两类不同的验证因素：你知道的（密码）、你拥有的（手机认证 App、硬件安全密钥）、你本身的特征（指纹/人脸）。区分两个应用场景：
- **登录层面的 MFA**：密码之外再输入一次动态验证码才能登录 IAM/控制台，防止密码泄露后被盗用登录。
- **S3 MFA Delete**：已经正常登录的前提下，对"永久删除对象版本"或"关闭 Versioning"这类高风险操作，额外单独再要求一次 MFA 验证，是更细粒度的操作级保护。

## 六、SAA 考频参考
- **RDS Proxy**：高频考点，常见考察角度是"Lambda 连接数耗尽该选什么"、"Aurora failover 后如何更快恢复连接"，以及本笔记第一节这种"连接问题 vs 数据丢失/持久化问题"的混淆陷阱。
- **Read Replica**：高频，核心是"读写分离减轻主库负担"以及"最小运维开销"这类描述下的首选方案。
- **S3 Requester Pays / Versioning + MFA Delete**：都是常见考点，注意题目问的是"谁付钱"还是"防止误删"，对应选不同机制，不要和跨账号权限、KMS 加密等选项混淆。
