# Cognito User Pools vs Identity Pools, and Distributed Transaction Pitfalls

## 1. なぜ AWS Cognito を使うのか

自前で認証（ログイン・パスワード管理）を実装するのは非常にリスクが高い。考慮すべき点が多すぎる：

- パスワードの加塩ハッシュ化（Salted Hash / Bcrypt・Argon2）
- ブルートフォース対策、アカウントロック
- MFA（多要素認証）
- パスワードリセットのメール送信フロー
- OAuth2 / OIDC による SSO（シングルサインオン）
- 医療系なら HIPAA / APPI などのコンプライアンス対応

これらを丸ごと AWS の認証専用マネージドサービスに委譲することで、パスワードそのものを自社 DB に一切保存せずに済み、セキュリティ責任の大部分を AWS 側に転嫁できる。

## 2. Salted Hash とは

- **Hash（ハッシュ）**: 平文パスワードを一方向・不可逆な文字列に変換する処理。DB にはこのハッシュ値だけを保存し、ログイン時に再ハッシュして比較する。
- **Salt（塩）**: ハッシュ化前にランダムな文字列を混ぜること。同じパスワードでも保存されるハッシュ値が毎回異なるため、事前計算済みの対照表（レインボーテーブル）による解析を防げる。

## 3. Cognito User Pools vs Identity Pools（SAA 頻出）

| | User Pools | Identity Pools |
|---|---|---|
| 役割 | **認証**（Authentication）＝「あなたは誰か」 | **認可**（Authorization）＝「あなたは何ができるか」 |
| やること | サインアップ・ログイン・JWT トークン発行 | Cognito のトークンを、S3/DynamoDB などにアクセスできる一時的な IAM 認証情報に交換する |
| 出力 | JWT（ID Token / Access Token） | 一時的な AWS アクセスキー（STS） |

この2つの役割の違い（認証 vs 認可）は SAA で頻繁に問われる典型的な引っ掛けポイント。

## 4. なぜ Cognito は別サービスとして分離されているか

- 自社 DB とは物理的に全く別のシステム（AWS 側のリモートサーバー）。
- 両者は直接繋がっておらず、**バックエンドのコードが仲介者となって HTTP API 経由で両方に指示を出す**ことで連携している。

```
[自社DB] <--DBプロトコル--> [バックエンドAPI] <--HTTP API（インターネット経由）--> [AWS Cognito]
```

DB と Cognito は互いの状態を知らない。バックエンドが片方の失敗を検知して明示的に埋め合わせ（補償処理）をしない限り、両者は簡単に「歯車がズレた」状態になる。

メリット:
- **複数クライアント（Web / iOS / Android / 管理画面）が同じ Cognito を呼ぶだけで SSO が実現できる**。各クライアントが個別にパスワードテーブルを持つ必要がない。
- 認証ロジックとビジネスロジックが分離され、アーキテクチャ上デカップリングされる。

## 5. データベースの「トランザクション」とは（FIFO とは別物）

トランザクション（Transaction）は「**全部成功するか、全部失敗して元に戻すか**」を保証する仕組み（Atomicity）。FIFO（先入れ先出し）は「処理する順番」の話であり、無関係。

例：銀行振込
- Step A: 自分の口座から100円引く
- Step B: 相手の口座に100円足す

トランザクションが無ければ、Step A の直後に落ちた場合 100円が消えるだけ。トランザクションがあれば、Step B が失敗した時点で Step A も自動的に巻き戻される（Rollback）。

## 6. 「DB はコミット済み、Cognito 更新だけ失敗」という典型的な非原子性バグ

**問題のある実装順序:**
1. 自社 DB に複数テーブルを書き込み、**即座に Commit（確定）**
2. その後に Cognito へ HTTP API でメールアドレス更新を送る
3. Cognito 側の厳格なバリデーション（全角文字などを拒否）で 500 エラー

DB は他システム（Cognito）の成否を待たずに確定してしまっているため、Cognito だけ更新に失敗すると **DB とCognito の状態が食い違ったまま残る**。API が 500 を返したからといって「何も書き込まれていない」と推測するのは誤り——実際には DB 側は先に確定済みという場合がある。

なぜこの順序で書かれるか（開発者側の意図）:
- **DB トランザクション中に外部 HTTP リクエストを挟むと危険**（レイテンシでロックが解放されずコネクションプールが枯渇し得る）という設計上の教訓から、「DB を先にさっさと確定してロックを解放し、最後に外部同期する」という順序を選んだと考えられる。
- 一方で、DB の `email` カラムは単なる `VARCHAR` で全角文字も無条件に受け入れてしまうが、Cognito 側は ASCII ベースの厳格なメール形式チェックを行うため、**「自社 DB を通っても Cognito では拒否される」ギャップ**が生まれる。

### さらに危険な「静かな偽成功」

この中間状態（DB は新メール、Cognito は旧メールのまま）を、既存の「メール変更 API」で修復しようとすると、その API が **旧メールで検索 → 該当行が見つからない（0 rows affected）→ 何もせず 200 OK を返す** という実装だった場合、運用者は「直った」と誤認したまま Cognito 側は永遠に古いメールのまま残る。

**教訓**: API のレスポンスコードだけで内部状態を推測してはならない。障害復旧時は必ず実データ（DB の実レコード、Cognito の実属性）を直接確認してから対処する。

## 7. 正しい設計への改善方向

1. **順序を入れ替える（コスト最小）**：
   - 現状: DB 書き込み・コミット → Cognito 更新
   - 改善後: Cognito 更新を先に呼び、成功した場合のみ DB トランザクションを開始してコミットする
   - 効果: Cognito のバリデーション（全角文字など）で失敗した場合、その時点で処理を中断でき、DB トランザクションは一度も開始されない。システムは常に「変更前のクリーンな状態」を維持できる。
2. **補償処理（Saga パターン）を入れる**：業務上どうしても DB を先に書く必要がある場合は、`setup-staff` が Cognito 側の例外を捕捉する `catch` ブロックの中で、能動的に SQL を発行して DB を `from_email`（元の状態）へ戻す処理を必ず書く。
3. **`/internal/change-id` の「静かな偽成功」脆弱性を修正する**：
   - `change_id.go` の該当ロジックで `rowsAffected == 0` になった場合に、無条件で `200 OK` を返して正常終了してはならない。
   - 代わりに、DB 側で該当行が見つからなかった場合は Cognito 側の状態も確認するか、あるいは即座に `404 Not Found` / `400 Bad Request` を返してエラーとして扱い、「実際は何もしていないのに成功したように見える」状態を防ぐ。

これら3点はいずれも今回発見した本番障害（setup-staff の非原子性設計＋change-id の静かな偽成功）の根本原因に対応しており、運用手順書（Runbook）による人力での都度診断・補正ではなく、コード側での恒久対応として技術的負債チケットに切り出す価値がある。

## 8. SAA 試験での位置付け

- Cognito は 2014年発表、User Pools は2016年に追加。SAA では **ほぼ毎回 2〜3 問**出題される高頻出トピック。
- 出題の分水嶺は常に **User Pools（認証）vs Identity Pools（認可・一時 IAM クレデンシャル交換）** の役割の違い。
