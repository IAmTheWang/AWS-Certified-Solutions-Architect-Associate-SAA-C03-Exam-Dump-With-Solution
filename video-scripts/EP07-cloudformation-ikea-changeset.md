# EP07｜像宜家一样用 CloudFormation：Change Set 为什么能救生产数据库

*系列：AWS 人话课 · 时长 3:00 · 来源：`notes/CloudFormation-ChangeSet-and-Stack-Concepts.md`*

**一句话核心**：改一行模板可能触发"删除后重建"，对有状态资源等于丢数据；Change Set 让你先看清单再执行，Stack Policy 和 DeletionPolicy 在后面兜底。

**贯穿比喻**：宜家说明书体系——模板 = 说明书；Stack = 拼好的家具；有状态资源 = 装满书的书架。

---

## 0:00–0:15 钩子

**画面**：一个装满书的书架被一只手拆散，书掉了一地。

**口播**：
> 你只改了一行配置，CloudFormation 却把生产数据库，删了重建，数据全没了。这种事故怎么避免？先用宜家的说明书，把几个概念搞懂。

## 0:15–1:00 宜家比喻

**画面**：说明书 → 家具；三套环境三件家具；书架和鱼缸高亮。

**口播**：
> 模板，就是宜家的组装说明书，写清楚用几块板、几颗螺丝。Stack，是照着说明书拼出来的那件家具。同一份说明书能拼好几件，对应现实里 dev、stg、prd 三套环境，各是一个 Stack。关键是有状态资源：已经放满书的书架，已经装满水的鱼缸，一旦拆了重装，里面的东西就没了。对应数据库 RDS、EBS 硬盘这些，保存着业务数据。无状态的，比如 Lambda 函数，删了重建毫无损失。EBS 可以理解成挂在 EC2 上的一块移动硬盘，是最典型的有状态资源之一。

## 1:00–1:40 Change Set：预演体检报告

**画面**：清单：Add、Modify、Replace，Replace 那行闪红。

**口播**：
> 有些属性可以原地修改，有些一改，就会触发隐式替换，也就是先删旧的，再建新的。你直接 update，要执行到那一步才知道。Change Set，就是动手前的体检报告：拿新模板和现有 Stack 对比，列出每个资源是新增、修改，还是替换。看到有状态资源要被 Replace，你可以直接放弃，回去改模板，比如给它加上 DeletionPolicy Retain。对比一下：直接 update，看不到会不会删重建，误删风险高；用了 Change Set，提前看到完整清单，随时可以叫停。

## 1:40–2:15 Stack Policy：贴在家具上的纸条

**画面**：书架上贴一张纸条"不许拆"，有人拿着螺丝刀被拦住。

**口播**：
> 还有一道闸门，叫 Stack Policy，像贴在书架上的一张纸条：不管说明书后面怎么改，这个书架不许拆掉重装。哪怕有人没看 Change Set，或者看漏了，CloudFormation 也会在执行阶段，直接拒绝替换这个资源。Change Set 是动手前主动看一眼，Stack Policy 是硬性兜底，两个互补。它最常见的用法，就是保护数据库这类有状态资源。

## 2:15–2:50 三个进阶概念

**画面**：三张小图：小册子、发给多个房间、现场核对。

**口播**：
> 顺带三个进阶概念。Nested Stack，是把太厚的说明书拆成几本小册子。StackSets，是同一份说明书发给多个房间，也就是多个账号、多个区域，批量部署。Drift Detection，是拿着说明书去现场核对，有人在控制台手动拧了螺丝、加了个抽屉，它能查出来。这也是为什么强调，基础设施别手动改。如果你听说过 Terraform，它的 plan 命令，功能和 Change Set 很像，但它是跨云的第三方工具，SAA 考试不考。

## 2:50–3:00 结尾

**画面**：一句话总结字幕。

**口播**：
> 记住：有状态资源，动手前先看 Change Set。下期讲一个真实事故：CI 绿了五天，部署却全挂了。
